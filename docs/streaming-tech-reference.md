# 스트리밍 서비스 기술 레퍼런스 — 기능별 Best Practice

> 작성 2026-11-05 · 과제 필수/선택 기능별로 "어떤 기술을 쓰는가 + 그 기술이 무엇을 하는가"
> 전제: **웹앱** 기준. 핵심 통찰 — 이 과제는 **①평범한 웹앱(회원·CRUD) + ②실시간 영상 전송** 두 세계의 결합이고, ②가 난이도의 대부분이다.

---

## 0. 가장 먼저 알아야 할 3개 용어 (이거 모르면 다 헷갈림)

| 용어 | 한 줄 | 지연 | 쓰는 곳 |
|---|---|---|---|
| **RTMP** | 옛날부터 쓰는 **송출(업로드)** 프로토콜. OBS가 서버로 영상 쏠 때. | — | 송출자→서버 (인제스트) |
| **WebRTC** | 브라우저 내장 **초저지연 양방향** 영상/음성. 화상통화 그 기술. | **<1초** | 송출·시청 둘 다 (저지연) |
| **HLS** | 영상을 잘게 쪼갠 조각파일을 HTTP로 뿌리는 **시청(다운로드)** 방식. 유튜브·넷플 방식. | 2~10초 | 서버→다수 시청자 (확장성) |

> **왜 둘(WebRTC vs HLS)로 나뉘나:** WebRTC는 빠르지만 시청자 1만 명으로 못 키움(서버 부담 큼). HLS는 느리지만 CDN으로 **무한 확장**. 그래서 "소통형 저지연 방"은 WebRTC, "대중 시청"은 HLS를 쓴다.

**WHIP / WHEP** = WebRTC를 "웹 표준 HTTP 방식"으로 쓰게 해주는 신호 규약. WHIP=송출, WHEP=시청. 순수 웹앱으로 WebRTC 하려면 이걸 쓴다.

## 1. [필수] PC 라이브 방송 — 화면·소리·마이크 송출

**브라우저가 화면/소리/마이크를 캡처하는 법 (전부 웹 표준 API):**

| 기술 | 무엇을 하는가 |
|---|---|
| `navigator.mediaDevices.**getDisplayMedia()**` | **화면 공유** 캡처. 옵션으로 **탭/시스템 소리**까지 같이 잡음 |
| `navigator.mediaDevices.**getUserMedia()**` | **마이크**(와 웹캠) 캡처 |
| **Web Audio API** | 화면 소리 + 마이크를 **하나로 믹싱** |

**캡처한 걸 서버로 보내는 법 (두 갈래):**

- **A. 순수 웹 (권장, best practice):** 브라우저 → **WebRTC(WHIP)** → 미디어 서버. 설치 없이 웹페이지에서 바로 방송. 지연 1초 미만.
- **B. 전문 송출:** **OBS Studio** → **RTMP** → 서버. 화질·안정성 최고지만 **별도 프로그램 설치** 필요(= 순수 웹앱 아님). 많은 서비스가 "고급 송출자용"으로 병행 제공.

> **추천:** 웹앱 과제이니 **A(WHIP)**를 메인으로, 여유되면 B(RTMP)도 받으면 가산.

## 2. [필수] 모바일 라이브 방송 — 카메라·마이크 송출

- **모바일 웹 브라우저:** `getUserMedia({video, audio})`로 **카메라+마이크** 캡처 → **WebRTC(WHIP)**로 송출. PC와 거의 같은 코드.
- (네이티브 앱이라면: Android **CameraX** / iOS **AVFoundation**로 캡처 → 인코딩 → RTMP/WebRTC. 과제가 웹앱이면 불필요.)

> 핵심: 모바일도 **PC와 같은 WHIP 경로** 재사용하면 구현이 하나로 통일됨. 카메라 전/후면 전환만 추가(`facingMode`).

---

## 3. [필수] 방송 관리 — 등록·조회·수정·삭제 + 실시간 시청

여기서 **두 종류의 "데이터"**를 구분해야 한다:

**(a) 방송 메타데이터 = 평범한 CRUD (익숙한 웹 영역)**
- 제목·썸네일·방송자·상태(온에어 여부)·시청자 수 → **일반 DB(RDB: PostgreSQL/MySQL)** + **REST API**
- 등록/조회/수정/삭제 = 그냥 CRUD. 어렵지 않음.

**(b) 실제 영상 = 미디어 서버가 담당 (새로운 영역)**

| 기술 | 무엇을 하는가 |
|---|---|
| **미디어 서버** (MediaMTX / SRS / LiveKit / Janus) | 송출(RTMP/WHIP)을 **받아서** 시청용(HLS/WHEP)으로 **변환·중계**. 이 과제의 심장 |
| **FFmpeg** | **트랜스코딩** — 원본을 여러 화질(1080p/720p/480p)로 변환 = **ABR**(끊김 없이 화질 자동조절) |
| **hls.js** | 브라우저에서 **HLS 영상 재생**해주는 JS 라이브러리 (HTML5 video가 HLS 직접재생 못해서 필요) |
| **CDN** | HLS 조각파일을 전 세계 뿌려 **대규모 시청** 감당 (과제 규모면 선택) |

**"실시간 시청"의 실제 동작:** 시청자가 방송 페이지 열면 → DB에서 "온에어?" 확인 → 미디어 서버의 **HLS URL**(또는 WHEP)로 플레이어 연결 → 영상 재생. "실시간"은 **라이브 재생**을 뜻하지, 메타데이터 폴링이 아님.

> **최단 경로:** **MediaMTX** 하나면 RTMP/WHIP 수신 + HLS/WHEP 출력을 **한 통으로** 다 해줌. 1일차 데모 가능.

## 4. [필수] 사용자 인증 및 인가

**두 단어를 먼저 구분 (자주 헷갈림):**
- **인증(Authentication)** = "너 **누구냐**" → 회원가입·로그인·로그아웃
- **인가(Authorization)** = "너 이거 **해도 되냐**" → 방송 소유자만 수정·삭제

| 기술 | 무엇을 하는가 |
|---|---|
| **비밀번호 해싱: bcrypt / argon2** | 비번을 복호화 불가능하게 저장. **평문 저장 절대 금지** |
| **세션-쿠키** 또는 **JWT** | 로그인 상태 유지. 세션=서버가 기억(httpOnly 쿠키), JWT=토큰에 담아 전달(access+refresh) |
| **Spring Security / Passport.js / NextAuth** | 위 흐름(로그인·세션·보호된 라우트)을 묶어주는 프레임워크 |
| **OAuth 2.0 / 소셜로그인** | 네이버·구글 계정으로 로그인 (선택) |
| **인가: 소유권 검사(ownership check)** | 방송 수정/삭제 API에서 `방송.ownerId == 로그인유저.id` 확인. 아니면 403 |
| **스트림키(stream key)** | 송출 인증용 비밀 키. 이게 있어야 그 방송으로 송출 가능 → **노출되면 도용**, 그래서 보호 |

> 베스트 프랙티스 핵심 3개: ① 비번은 argon2/bcrypt, ② 세션 쿠키는 httpOnly+Secure, ③ **인가는 모든 변경 API에서 소유권 재확인**(프론트에서 버튼 숨기는 걸로 끝내면 안 됨).

## 5. [선택/가산점]

### 댓글 (실시간 채팅)
| 기술 | 무엇 |
|---|---|
| **WebSocket** (STOMP / Socket.IO) | 서버↔브라우저 **양방향 상시연결**. 댓글은 HTTP가 아니라 이걸로 (실시간 푸시) |
| **메시지 영속화: DB** | 다시보기·기록용 저장 |
| (대규모) **Redis Pub/Sub** | 서버 여러 대로 채팅 **팬아웃** |

### 도네이션
| 기술 | 무엇 |
|---|---|
| **PG(결제대행): Toss Payments / 아임포트(PortOne)** | 실제 결제 처리 |
| **멱등성(idempotency) + 원장(ledger) DB** | 중복결제 방지·정산·환불. **진짜 어려운 부분은 영상이 아니라 돈** |
| **WebSocket 알림** | 후원 실시간 알림 오버레이 |

### 녹화 및 다시보기 (VOD)
| 기술 | 무엇 |
|---|---|
| **미디어 서버 녹화** (MediaMTX/FFmpeg) | 라이브를 파일로 저장 |
| **오브젝트 스토리지: S3 / MinIO** | 녹화 파일 보관 |
| **VOD용 HLS** | 저장된 파일도 HLS로 변환해두면 재생기 그대로 재사용 |

## 6. 추천 스택 (opinionated, 과제 규모)

```
프론트:   React/Next.js + hls.js + 브라우저 WebRTC API
백엔드:   Spring Boot(or Node/NestJS) + REST + WebSocket
인증:     Spring Security + JWT(access/refresh) + bcrypt
DB:       PostgreSQL (유저·방송·댓글) + Redis (세션/채팅 팬아웃)
미디어:   ★ MediaMTX (RTMP/WHIP 수신 → HLS/WHEP 출력) + FFmpeg(트랜스코딩)
저장:     S3/MinIO (썸네일·VOD)
결제:     PortOne/Toss (도네이션)
```

## 7. 절대 직접 만들지 말 것 (ponytail)

| 만들지 마라 | 대신 |
|---|---|
| 영상 코덱·인코더 | 브라우저 WebRTC / FFmpeg |
| 미디어 서버 | MediaMTX·SRS·LiveKit |
| 플레이어 엔진 | hls.js / video.js |
| 인증 프레임워크 | Spring Security / Passport |
| 결제 | PG사 SDK |

**네가 실제로 짜는 코드:** 방송 CRUD API, 인증·소유권 로직, 미디어서버와 연동(스트림키 발급·방송 시작/종료 처리), 프론트 UI, 채팅·도네이션 비즈니스 로직. **영상 자체를 나르는 건 전부 기성품에 맡긴다.**

### 다음 한 걸음
가장 불확실한 ②영상 구간을 **먼저 검증**하라: MediaMTX 띄우고 → 브라우저 WHIP로 송출 → 다른 탭에서 HLS로 시청. 이 **1-송출 1-시청 루프**가 돌면 나머지(CRUD·인증)는 익숙한 웹 작업이다.
